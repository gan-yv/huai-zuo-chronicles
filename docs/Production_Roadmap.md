# 《春江花月夜：异本》制作路线与里程碑

版本：0.1  
日期：2026-11-17  
制作条件：个人开发、每天约45分钟、AI 辅助、Unity 2D  

## 1. 当前判断

项目已经完成足够的前期设计，可以进入原型制作。

目前不缺设定，缺的是以下验证：

- 玩家能否理解异文为什么重要。
- 玩家是否会在两个版本之间真正犹豫。
- 文字选择是否有足够的游戏感。
- Unity 中的点击、对话和比对界面能否顺畅完成。

因此路线遵循一个原则：

> 先完成一个能判断好坏的最小版本，再决定是否扩展内容。

## 2. 阶段总览

| 阶段 | 目标 | 预计工作时段 | 完成标准 |
|---|---|---:|---|
| M0 项目基础 | 本地 Git、私有 GitHub 仓库、Unity 工程 | 2～3次 | 能提交、推送并打开 Unity |
| M1 核心灰盒 | 书坊单场景完整循环 | 6～8次 | 调查、比对、选择、结果、重开可运行 |
| M2 Demo v0.1 | 8～12分钟完整测试版 | 8～12次 | 有修复室、书坊、结果和 Windows 构建 |
| M3 试玩修正 | 验证目标玩家是否理解并想继续 | 3～5次 | 3名以上玩家完成并给出可用反馈 |
| M4 美术切片 | 正式背景、人物和界面 | 8～12次 | 画风统一，文字可读，构建稳定 |
| M5 扬州卷 | 25～30分钟正式内容 | 后续评估 | 有完整局部闭环，可独立游玩 |
| M6 海陵与通州 | 扩展完整三卷 | 后续评估 | 通过正式主线闭环 |

预计只能用“工作时段”衡量，不承诺日历日期。45分钟包含启动、试玩和提交时间，不是纯制作时间。

## 3. M0：项目基础

### 目标

建立一个不会丢失资料、可以回退、不会把 Unity 构建垃圾提交进去的项目仓库。

### 交付物

- 本地 Git 仓库。
- Git LFS 已启用。
- 私有 GitHub 仓库。
- 首个设计文档提交。
- GitHub Milestone `M0：项目基础`。
- Unity 2D 工程放在 `UnityProject/`。

### 不在本阶段做

- 不写剧情分支代码。
- 不定最终美术。
- 不购买插件。
- 不制作宣传材料和商店页面。

### 通过条件

- `git status` 干净。
- GitHub 能看到完整文档。
- 新电脑或新目录可以克隆仓库。
- Unity 工程可以正常打开。
- `Library/`、`Temp/`、`Logs/` 和构建产物没有进入远程仓库。

## 4. M1：核心灰盒

### 目标

只做书坊场景，验证文字调查是否值得玩。

### 内容

- 一个色块书坊背景。
- 两个可点击人物：陆掌柜、顾师父。
- 两份可读文本：节目册、旧唱词。
- 玩家只能选择调查其中一人。
- “待/照”双页异文比对。
- 一张记录证词、异文和印刷方式的残缺校勘笺。
- 一次二次确认。
- 两个简短结果。
- 重新开始。

### 不做

- 不修复室序章。
- 不做海陵来信。
- 不做正式美术。
- 不做配音。
- 不做存档。
- 不做多结局总结。

### 通过条件

- 从进入场景到结束不超过5分钟。
- 玩家不看说明也能知道自己正在选择节目册用字。
- 两名测试者中至少一人愿意重玩另一条分支。
- 核心问题不是界面卡住，而是玩家能否理解选择。

### 关键决策门

如果玩家把所有选择都当成“明显的正确答案”，停止扩展内容，重写两个人的理由，而不是增加第三个选项。

## 5. M2：Demo v0.1

### 目标

做出 8～12 分钟、可用于外部试玩的完整流程。

### 内容

- 修复室发现缺字。
- 进入扬州书坊。
- 调查陆掌柜或顾师父。
- 在“待”和“照”之间选择。
- 看到局部灯会结果。
- 查看由本次选择生成的残缺校勘笺。
- 收到海陵来信并结束。
- 可以重新开始。

### 通过条件

- 从标题到结束无死路。
- 所有正式文本完成，没有 `TODO`。
- 玩家无需开发者解释即可完成。
- Windows 64 位构建可以在另一台电脑运行。
- 3～5名玩家完成基础试玩。

## 6. M3：试玩与修正

### 目标

验证核心玩法，而不是验证美术漂亮程度。

### 记录

- 玩家多久知道目标。
- 玩家是否理解“一人只能调查一个”的限制。
- 玩家在异文选择前犹豫多久。
- 玩家能否说出选择理由。
- 是否有人主动重玩。
- 是否有人想继续看海陵卷。

### 通过条件

- 至少3人能独立完成。
- 至少3人能准确说出两个版本的差别。
- 至少3人表现出继续看的意愿。
- 没有人因为 UI 卡住超过1分钟。

### 失败处理

- 目标不清：重写开场前六句。
- 选择像猜题：重写两个人物动机。
- 异文无感：缩短前后对白，让选择更早出现。
- 阅读疲劳：先删文本，不加动画。

## 7. M4：正式美术切片

### 目标

用有限素材建立正式视觉方向，而不是制作全部资源。

### 内容

- 修复室背景。
- 扬州书坊背景。
- 河岸结果背景。
- 陆掌柜、顾师父各一张半身像。
- 每人两个表情。
- 双页书稿界面。
- 一套正式按钮、字体和点击反馈。

### 通过条件

- 三张背景使用同一光照与材质逻辑。
- 立绘与背景比例协调。
- 中文在 1920×1080 和 1280×720 下均可读。
- AI 生成图中的文字、印章和建筑细节已人工检查。

## 8. M5：扬州卷

只有 Demo 验证通过才进入。

目标为25～30分钟：

- 第一位证人和更多证物。
- 更完整的节目册冲突。
- 卷尾灯会演出。
- 不同文本选择造成明显不同的公共记忆。
- 正式主题音乐和基础环境声。

扬州卷完成前，不制作海陵和通州完整场景。

## 9. 每周节奏

建议一周分配：

- 2次：Unity 和技术流程。
- 1次：对白与剧情修订。
- 1次：界面、美术或音频。
- 1次：试玩、记录和 GitHub 整理。
- 周末：不强制加班，只处理阻断问题。

每次45分钟只完成一个可验收小任务。遇到新点子先记入待办，不立刻扩进当前版本。

## 10. Git 工作流

- `main` 始终可打开、可运行。
- 一次开发只使用一个功能分支。
- 每个阶段结束打标签，例如 `m1-core-loop`。
- 每天至少提交一次；完成一个可运行节点后推送。
- 大图、音频和字体使用 Git LFS。
- 设计与范围变化写入文档后再改代码。

## 11. 决策门

### 门1：仓库可用

没有本地提交和远程推送，不开始 Unity 正式工程。

### 门2：灰盒好玩

玩家能理解、犹豫并愿意重玩，才进入完整 Demo。

### 门3：Demo可用

3～5名目标玩家完成并给出反馈，才进入正式美术。

### 门4：扬州卷完整

首卷有局部闭环且能独立玩完，才扩展海陵和通州。

## 12. 当前禁止事项

- 不继续扩写旧时代、旧城市和无关支线。
- 不先做几十张 AI 美术。
- 不先做完整战斗、经营或城市模拟。
- 不为“以后可能用到”提前编写通用引擎。
- 不同时完成三座城市。
- 不在核心玩法未验证时做商店页面和宣传片。

## 13. 最近三次工作时段

### 第1次：本地与远程仓库

- 初始化 Git。
- 首次提交设计文档。
- 创建私有 GitHub 仓库并推送。

### 第2次：Unity 工程

- 建立 Unity 2D 工程。
- 设置分辨率与版本控制。
- 建立标题与空场景。
- 提交 `Assets/`、`Packages/`、`ProjectSettings/`。

### 第3次：对话框架

- 显示一段旁白。
- 点击推进。
- 进入书坊占位场景。
- 在 GitHub 留下第一段可运行记录。

完成这三次后，再开始书坊调查逻辑。
